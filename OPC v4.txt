理解。你要的是 **v4：把 v3 的骨架保持不变，但把每一个"我要自己写"的环节，替换成"押标准 + 用开源件"**。我先做一轮实地调研，把当前真实可用的项目查清楚，再出细化到点击和提示词的落地文档。# 一人软件公司 v4：押标准 · 用开源件 · Loop Engineering 终版落地手册

> v1 护城河 = 权限分离；v2 = 结构性消灭确认对话框；v3 = 目标下沉（AI 自己派活）。
> **v4 = 骨架收缩到 1500 行，其余全部换成开源件，并加一条把上游进步自动吸进产线的管道。**

# 第 0 部分：这次调研改变了什么（先看这 5 条，其余都是细节）

| # | 发现 | 对方案的强制性影响 |
|---|---|---|
| 1 | **spec-kit 成熟到可以直接当"意图层格式"** | github/spec-kit 是 MIT 许可的意图驱动 harness，工作于 30 多个 AI 编码 agent（CLI 与 IDE 两类），仓库已有 90k+ stars、8k+ forks。它自带 constitution.md，用来确立项目不可协商的原则，并有 跨产物一致性/覆盖度分析命令（在 tasks 之后、implement 之前跑），以及生成质量清单的命令（相当于"给英文写单元测试"）。**结论：我的 CHARTER/波次/卡片全部改用 spec-kit 的文件格式，并把 analyze + checklist 当作"波次物化前的机器门禁"。但 `/speckit.implement` 永不采用**——那一步会接管控制流。 |
| 2 | **供应链是当前最高频的真实杀伤，必须偏执** | 2026 年 3 月攻击者利用 trivy-action 的 pull_request_target 配置错误窃取组织与仓库 secrets，随后用这些凭证在 PyPI 上给 LiteLLM 植入后门；LiteLLM 的 CI 从 apt 拉未固定版本的 Trivy，被污染的 action 就此偷走了 PYPI_PUBLISH token；GitHub 上的源码从未被改动，攻击只存在于 PyPI 制品里，审仓库的人根本看不见。**结论：新增三条铁律——① 任何依赖不登记进 `UPSTREAM.yaml` 就红；② 新版本必须过 7 天冷静期才允许自动升级；③ 永不使用 `pull_request_target`，PR 触发的 job 零 secrets（这条 v1 就有，现在有血案背书）。** |
| 3 | **12 个巡检 lens 全部有现成工具，一个都不用自己写** | 见第 3 部分表格。全部输出 SARIF 或 JSON，天然适配我的"证据在前、LLM 只做归类"设计。 |
| 4 | **编排框架的红线被实测证据确认** | 开源编排器都用 git worktree 解决并行执行，但大多仍把任务对齐、冲突解决、合并决策留给你自己；它们默认用跳过权限确认的参数运行 agent；Vibe Kanban 背后的 Bloop 在 2026 年初宣布关停，项目转为社区维护。**结论：v3 红线不变——编排框架只能当"单卡执行器"塞进接缝 B，绝不许跨卡调度。** |
| 5 | **我的提示词本身需要 CI** | promptfoo 是 MIT 的开源 CLI，有三档断言：确定性断言（contains/regex/latency/cost）免费即时，模型评分断言 llm-rubric 交给另一个 LLM 判主观质量，断言失败时非零退出，可用 pass-rate 阈值在 CI 里拦真回归、容忍模型抖动。**结论：新增第 8 环——`prompts/**` 的每一次修改都必须通过 promptfoo 回归才能合并。这解决了 v3 唯一没解决的问题："谁来验证验证者"。** |

# 第 1 部分：开源件选型总表（五问判定器结论）

判定器（写进 `DECISIONS.md`，以后不再纠结）：
1. 要接管我的控制流吗？要 → 否。
2. 它挂了我是停摆还是降级？停摆 → 否。
3. 需要我长期运维有状态服务吗？需要 → 推迟。
4. 我能在 200 行内自己写出它 80% 的价值吗？能 → 自己写。
5. 产物是静态文件还是运行时依赖？静态文件优先。

## 2.1 分层与格式（"押格式不押项目"）

# 第 3 部分：12 个 lens 的工具映射（每一个都有 pinned 工具，一行自研代码都不要写）

| lens | 确定性工具（pin 版本） | 输出 | 频率 | LLM 的职责 |
|---|---|---|---|---|
| `test-effectiveness` | **Stryker**（JS/TS）/ **mutmut** 或 **cosmic-ray**（Py）/ **go-mutesting**（Go）这三者分别覆盖 Python 与 Go 的变异测试 | mutation score JSON | **夜间**，只对近 14 天改动文件 | 解释存活变异体意味着什么漏测场景 |
| `contract-drift` | **oasdiff** + **Spectral** | oasdiff JSON + lint 报告 | 每次 PR（契约路径） | 判断哪边错了 |
| `deps-risk` | **osv-scanner** + **Syft/Grype** + 许可证白名单 | SARIF/JSON | 每日 | 排优先级、给替代方案 |
| `secret-leak` | **gitleaks**（PR 阻塞）+ **TruffleHog**（每周全历史，只报 verified） | SARIF | PR + 每周 | 真假阳性判定 + 轮换方案 |
| `ci-security` | **zizmor** + **pinact --check** | SARIF | 每次 PR | 归因（触碰 workflow 的卡强制 critical） |
| `error-path` | **Semgrep** 自定义规则（catch-swallow / 裸 except / 无超时 IO / 无重试网络） | SARIF | 每日分片 | 判断哪条命中 Q1 数据丢失路径 |
| `dead-code` | **vulture**（Py）/ **knip** 或 **ts-prune**（TS）/ `deadcode`（Go）+ git 最后修改时间 | JSON | 每日分片 | 死代码还是待用扩展点 |
| `dup-logic` | **jscpd** | JSON | 每日分片 | 是否值得抽象（受 N4 约束） |
| `observability-gap` | 自写 30 行：关键函数 × 日志/指标埋点覆盖矩阵 | JSON | 每周 | 指出"故障时你会瞎"的位置 |
| `perf-hotspot` | canary 耗时分解 + bundle size diff + N+1 检测 | JSON | 每日 | 对照 G2 判断是否超标 |
| `doc-as-test` | README/docs 里的命令**实际执行**，退出码非 0 即证据 | 退出码 | 每次 PR | 改文档还是改代码 |
| `reopen-cause` | `gh` 查近 30 天 reopen/revert/hotfix | JSON | 每周（retro） | 归因到"哪类卡系统性失败" |

**关键工程约束（照抄）**

- 变异测试**绝不进 PR 关键路径**：放在定时的夜间 workflow 里跑，先记录初始的变异击杀目标，再逐步上调。
- 用增量模式控成本：`--incremental` 会把结果持久化，后续运行跳过代码与测试都没变的变异体，再配合 `--mutate` 和 `--since` 把范围限定在当下相关的代码。
- 分片轮转不变（v3 设计）：`.loop/audit/shards.yml`，每天 2 片，每片只喂 `last_audited_sha..HEAD` 的 diff + 该片证据 JSON。**Token 恒定，不随仓库增长爆炸。**

| `gate/prompt-eval` | promptfoo（pass-rate 阈值） | 提示词回归 | 有 `prompts/**` 改动时 |
| `gate/verdict-binding` | 自写 40 行 | VERDICT 的 head_sha ≠ 当前 head_sha | standard/critical |
| `gate/build` `gate/test` | 你的语言原生 | — | 全部 |

> ⚠️ 关于 SARIF 上传的坑：GitHub 只在"发现涉及的所有行都包含在 PR diff 里"时才在 PR 上显示 code scanning 检查，这不直观但就是它的行为。所以 **每个 gate 都必须自己以退出码失败**，不要依赖 code scanning 的 PR 检查来阻塞。

# 第 6 部分：落地顺序（Day 0 → 第 8 周，点击级细节）

> 排序原则（比 v3 更严）：**先让循环无人化 → 再让"完成"可机器判定 → 再让 AI 找活 → 再让 AI 派活 → 最后接上游。**

# 第 10 部分：本质总结（v4 版）

```
人类写的是 CHARTER（意图），不是 issue（任务）
Planner 写的是提案（可否决），不是命令
AI 写的是 Finding（证据），不是结论
工具说的是发现（SARIF），不是感觉
Checker 说的是完成（可验证），不是模型自称完成
UPSTREAM 说的是可信（pin + 冷静期），不是 star 数
Journal 存的是记忆（不可篡改），不是平台的善意
```

六个 gate，每一个的通过条件都是机器可判定的。人类只出现在第一个（写章程）和唯一一个每周 gate（批波次）。

> 一人公司的终局不是"我一个人干了十个人的活"，
> 而是**"这套系统在我睡着时仍然知道自己该干什么、该怎么证明自己干对了、干错了怎么被发现、以及上游变好时怎么自动把好处吃进来"**。
>
> 骨架自己写且写得极小（≤1500 行），零件全部外包且全部可热插拔，然后花一次性成本建好升级环——从此**上游每一次进步都自动变成你的吞吐，而不是你的待办。**
> 人数恒等于一，判断权必须多于一，且没有任何一个判断者能自证自己是对的。
