## 0. 关键澄清（避免被误导）

外部审查曾称 canary "用 admin PAT 绕过分支保护"——**这是假的**。
`.loop/scripts/canary-chain.sh:76-79` 明确拒绝 `--admin`，改走 GraphQL `enqueuePullRequest` 进 merge queue；
线上 ruleset 的 `bypass_actors` 是空数组，任何 token 都绕不过分支保护。
真实风险只是"高权限 PAT 存为 repo secret"这一**密钥卫生问题**——本清单 + B2 即用于收敛它。

> 注：`GH_TOKEN` 只是 `gh` CLI 读取鉴权的**环境变量名**，不是独立 secret；它的值来自下列某个具体凭证
> （SCRIBE_GH_TOKEN / LOOP_CANARY_TOKEN / Conductor App token / GITHUB_TOKEN 等）。下表按真实来源归类，不单列 GH_TOKEN。

## 2. 按逻辑凭证组枚举（6 组）

### 组 A — 跨仓 PAT（repo secret，高权限令牌）⚠️ 密钥卫生重点

这是 B2 的核心关切：高权限 PAT 长期存为 repo secret，泄露面大、难以细分权限、轮换成本高。
建议迁移为 fine-grained PAT 或 GitHub App。

#### A1. `SCRIBE_GH_TOKEN`
- **承载身份**：loop-scribe-bot 的 PAT（个人访问令牌）
- **所需最小权限范围**：fine-grained PAT，仅授 `Cloudbird-Software/loop` 与 `Cloudbird-Software/<product-x>` 的 `issues:read` + `metadata:read`（导出 issues/PRs/comments/reviews/runs），以及 journal 仓库的 `contents:write`（clone + push 快照）。**不应**授 org 级 admin 或全 repo 写权限。
- **使用者 workflow**：`scribe.yml`（export 步骤 + journal commit/push 步骤）
- **轮换周期（建议）**：90 天
- **上次轮换日期**：unknown（仓库内无任何轮换记录）
- **责任人**：org admin（LOOP_HUMAN）

#### A2. `LOOP_CANARY_TOKEN`
- **承载身份**：loop-canary-bot 的 PAT
- **所需最小权限范围**：fine-grained PAT，仅授 `Cloudbird-Software/<product-x>` 的 `issues:write` + `pull-requests:write` + `contents:write`（push canary 分支）+ merge-queue enqueue。跨仓操作 product-x，GITHUB_TOKEN 作用域不够故必须保留 PAT；但应**最小化**到 product-x 单仓、仅上述权限。canary 走 merge queue 不用 admin，token 无需任何 admin/bypass。
- **使用者 workflow**：`canary.yml`（`Run canary chain` 步骤；本 PR 已把两个 Incident 步骤改用 GITHUB_TOKEN，进一步收缩本 token 的使用面）
- **轮换周期（建议）**：90 天
- **上次轮换日期**：unknown
- **责任人**：org admin（LOOP_HUMAN）

### 组 B — Conductor GitHub App（自动化主控 App）

#### B1. `CONDUCTOR_APP_ID` + `CONDUCTOR_APP_KEY`（App ID + private key，成对使用）
- **承载身份**：Conductor GitHub App（org 级安装，每运行由 `actions/create-github-app-token` 现换短期 token）
- **所需最小权限范围**：App 安装到 `loop` + `product-x`；权限 `issues:write`、`pull-requests:write`、`contents:read`、`actions:read`、`merge-queue:write`（按 conductor/upgrade/canary-survival 实际用到）。优于 PAT：token 短期、可吊销、有审计。
- **使用者 workflow**：`canary.yml`（survival 自检）、`conductor.yml`、`upgrade.yml`
- **轮换周期（建议）**：365 天（App private key 轮换）
- **上次轮换日期**：unknown
- **责任人**：org admin

### 组 C — Policy-R GitHub App（规则集只读 App）

#### C1. `POLICY_R_APP_ID` + `POLICY_R_APP_KEY`
- **承载身份**：Policy-R GitHub App（只读规则集）
- **所需最小权限范围**：组织级 `rulesets:read` + `metadata:read`。**仅读，无写**。org secret，visibility 须覆盖 loop repo（见 HUMAN-TODO B3）。
- **使用者 workflow**：`drift.yml`（`drift_check.py` 比对线上 ruleset vs `settings/*.json`）
- **轮换周期（建议）**：365 天
- **上次轮换日期**：unknown
- **责任人**：org admin

### 组 D — Policy-W GitHub App（规则集写入 App，apply 路径）

#### D1. `POLICY_W_APP_ID` + `POLICY_W_APP_KEY`
- **承载身份**：Policy-W GitHub App（规则集写入，apply 路径专用）
- **所需最小权限范围**：组织级 `rulesets:write`。**注意**：当前 apply 路径被 CHARTER N5 禁用（`policy.yml` apply 分支是 `::error:: + exit 1`），故实际未行使写权限；仅 `environment: policy` 人工审批后才可能调用。
- **使用者 workflow**：`policy.yml`（`environment: policy`，需人工审批）
- **轮换周期（建议）**：365 天；若长期不启用 apply，建议下架该 App 或收回 write 权限待用
- **上次轮换日期**：unknown
- **责任人**：org admin

### 组 E — GitHub Actions 默认 `GITHUB_TOKEN`（每运行临时签发，非存储 secret）

#### E1. `GITHUB_TOKEN`
- **承载身份**：GitHub Actions 每 run 临时签发的 `GITHUB_TOKEN`（身份 `github-actions[bot]`，作用域限当前仓 loop）
- **所需最小权限范围**：按各 workflow 的 `permissions:` 块授予——本 PR 后 canary/scribe 顶层均为 `contents: read`，issues:write 在 job 级按需展开（Incident 步骤）。**非存储 secret**，run 结束自动失效，无泄露面、无需轮换。
- **使用者 workflow**：`audit.yml`、`materializer.yml`、`drift.yml`、`nightly-rubric.yml`、`canary.yml`（Incident 步骤）、`scribe.yml`（隐式 checkout）
- **轮换周期**：不适用（每 run 签发）
- **上次轮换日期**：N/A
- **责任人**：GitHub 平台
