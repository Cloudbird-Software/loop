# 盲一半协议 (Blind-Half Protocol)

> 本文档定义 verify 沙盒在验证 standard/critical 卡时的盲阶段约束。
> 人类在搭建 verify 沙盒时以此为规格，确保实现与验证之间不可串通。

## 1. 目标

防止验证工在编写测试时偷看实现代码，从而根据实现行为（而非验收标准）调整期望值。
这是异构验证的核心：验证工与实现工使用不同模型，且验证工在盲阶段完全看不到 `src/`。

## 2. 三阶段流程

### 阶段一：盲阶段 (Blind Phase)

**输入**（验证工唯一可读的信息）：
- 卡片的 `acceptance` 数组（验收标准列表）
- `contracts/` 目录下的契约文件（schema / OpenAPI）
- `spec_ref` 指向的 PRD 段落（波次文件中的 objective 描述）

**严禁**：
- 打开 `src/` 下任何文件
- 运行应用以观察运行时行为来推断实现
- 与实现工同模型的沙盒通信

**任务**：
- 为每一条 AC 编写可执行测试
- 测试文件只能放在 `tests/` 下（`tests/acceptance/**` 除外）
- 期望值必须来自 AC 字面意思和契约定义，不可来自实现代码

**完成动作**：
- 运行 `loop save "verify: blind tests for <卡号>"`
- 此 commit 被记为 `blind_phase_commit`（记录其 SHA）
- 验证工在 VERDICT JSON 中必须如实填写 `blind_phase_commit` 字段

### 阶段二：执行定位阶段 (Execution Phase)

**解除限制**：
- 可读 `src/` 下所有文件
- 可运行测试

**任务**：
- 运行盲阶段编写的测试
- 对每个失败，判断是"实现有 bug"还是"测试写错了"
  - 实现有 bug → 在 PR 留评论：症状 + 最小复现 + 期望行为。**不修实现**。
  - 测试写错 → 修测试，并在 VERDICT 中如实记录"blind 阶段期望有误"

### 阶段三：结论 (Conclusion)

**产出 VERDICT JSON**（schema 见 `.loop/schemas/verdict.json`）：

```json
{
  "head_sha": "<当前 PR HEAD 的 commit SHA>",
  "blind_phase_commit": "<盲阶段结束时的 commit SHA>",
  "artifact_digest": "<tests/ 目录的 SHA256 摘要>",
  "test_plan_version": "<卡号>-<AC数量>",
  "acs": [
    {"id": "AC1", "pass": true, "evidence": "tests/unit/foo_test.py::test_ac1_bar"},
    {"id": "AC2", "pass": false, "evidence": "tests/unit/foo_test.py::test_ac2_qux"}
  ]
}
```

**提交**：运行 `loop verdict <file>`。若期间 head_sha 变化（实现工推了新 commit），系统拒收，验证工必须重跑阶段二、三。

## 3. blind_phase_commit 记录机制

1. 验证工在盲阶段结束时执行 `loop save`，loopd 落盘 commit 并 push。
2. 该 commit 的 SHA 被 loopd 自动写入 `.loop/verdict/blind_commit.txt`。
3. 验证工在 VERDICT JSON 中从此文件读取 `blind_phase_commit` 值。
4. `gate_verdict.py` 不直接校验 `blind_phase_commit` 的合法性（它校验 `head_sha`），
   但人类审计可通过对比 `blind_phase_commit` 之后的 diff 是否包含 `src/` 读取记录来
   判断盲阶段是否被违反（见第 4 节）。

## 4. 可读性审计方法

人类在 verify 沙盒中执行以下审计，确认盲阶段未被违反：

### 4.1 审计沙盒日志

verify 沙盒的 agent 会话日志（Trae 保存的终端历史）在 `blind_phase_commit` 之前不应出现以下任何模式：
- `cat src/`
- `open src/`
- `less src/`
- `head src/` / `tail src/`
- 编辑器打开 `src/` 路径的文件操作

### 4.2 审计测试内容

盲阶段测试的期望值不应依赖于实现细节：
- 合规：期望值来自 AC 文字或契约 schema
- 可疑：期望值是某个魔数或实现内部常量
- 违规：测试直接 import 实现内部私有函数并断言其返回值

### 4.3 审计 commit 顺序

```
git log --oneline --reverse blind_phase_commit..head_sha
```

此范围内的 commit 应只包含测试修复（在阶段二修测试错误时），不应包含对 `src/` 的修改。
若存在 `src/` 修改 → 盲阶段被违反，VERDICT 作废。

### 4.4 自动化检查（可选，未来 lens）

可编写一个 `blind-audit` lens 脚本：
1. 读取 VERDICT 的 `blind_phase_commit`
2. `git log --name-only blind_phase_commit..head_sha`
3. 若其中出现 `src/` 路径的修改 → Finding（severity=high）
4. 沙盒日志扫描：在盲阶段 commit 之前搜索 `src/` 读取模式

## 5. 搭建 verify 沙盒的检查清单

人类在创建 verify 沙盒时确认以下配置：

- [ ] `LOOP_ROLE=verify`（loopd 只领 verify 卡）
- [ ] `LOOP_MODEL` 与实现工不同（loopd 在 claim 时校验 `verify.model != impl.model`）
- [ ] 沙盒中无 `src/` 的预缓存（克隆仓库后可 `loop reset` 到干净状态）
- [ ] `.loop/verdict/` 目录可写（用于记录 `blind_phase_commit`）
- [ ] `loop verdict` 命令可用且指向 PR（用于提交 VERDICT）
- [ ] 日志采集开启（后台并行任务③ `collect-logs.sh`），便于盲阶段审计
- [ ] 沙盒有 `contracts/` 和 `waves/` 的读取权限（盲阶段唯一信息源）
