# 产品仓对齐架构（loop ↔ product-x ↔ 未来产品仓）

> 定稿 @2026-07-30。本文件是本轮讨论的架构结论存档，是 WAVE-13 全部卡片的规格来源。
> 相关 ADR：DECISIONS.md ADR-007 / ADR-008 / ADR-009。

---

## 0. 核心原则

> **loop 是控制面（机制），产品仓是数据面（内容）。
> 产品仓里绝不放机制的副本，只放对机制的引用。**

复制的东西越少，漂移就越少。这条原则推导出下面全部结论。

---

## 1. product-x 里留什么

### 留（产品特有 / 人写的内容）

| 路径 | 说明 |
|---|---|
| `CHARTER.md` | 唯一人类亲手写的东西。已由 AI 代拟，见 `templates/product-x/CHARTER.md` |
| `AGENTS.md` + `CLAUDE.md`（仅一行 `@AGENTS.md`） | agent 上下文真源 |
| `.specify/memory/constitution.md` | 由 CHARTER 的 N/Q 段生成 |
| `contracts/` | schema / OpenAPI，敏感路径 |
| `waves/` | 波次声明，与代码同库（ADR-002 已定） |
| `tests/acceptance/` | 契约级测试，CODEOWNERS 锁人类 |
| `.loop/CONTRACT.md`、`.loop/verify.sh`、`.loop/scripts/`、`.loop/audit/shards.yml` | 产品侧执行契约 |
| `.github/CODEOWNERS` | 敏感路径守卫 |
| **`LOOP.yml`（新增，本方案枢纽）** | 产品仓对 loop 实践的 **pin** |
| `.github/workflows/loop-*.yml`（薄壳） | 内容只有 `uses: Cloudbird-Software/loop/...@<sha>`，零逻辑 |

### 不留（机制，全部留在 loop）

`gates/*.py`、`lenses/*`、`conductor/*`、`loopd/*`、`prompts/*`、`settings/*`。

产品仓内出现这些目录的任何副本 → `gate/loop-conformance` 直接红（CHARTER N9 / Q7）。

### `LOOP.yml` 是什么

它对 loop 的作用，等同于 `UPSTREAM.yaml` 对外部依赖的作用：**把一个会变的东西钉死在一个可审计的版本上**。
模板见 `templates/product-x/LOOP.yml`。内容：`loop.version` + `loop.sha`（tag + 完整 40 位 SHA）、
启用的 lens 集合、gates profile、routing overrides、所需 secrets/environments 清单。

## 2. 怎么复制最好

### 2.1 种子：用 GitHub **Template repository**，不用 fork

product-x 设为 template repo，`Use this template` 一次性生成产品仓。

不用 fork 的原因：fork 带上游 PR 语义、可见性受父仓限制、独立演进麻烦、
且 fork 网络里的 Actions 与 secrets 行为有额外限制。

### 2.2 持续对齐：靠 **pin + reusable workflow**，不靠文件复制

产品仓永远调用 `Cloudbird-Software/loop/.github/workflows/reusable-*.yml@<sha>`。
机制在产品仓内**不存在副本**，因此机制层面**结构性地不可能漂移**。

这同时解决了一个当下真实存在的痛点：`F-002`（product-x `ci.yml` 缺 `merge_group` 触发器，
导致走 merge queue 的 PR 永久卡 `AWAITING_CHECKS`）。
若 CI 是模板文件，这个缺陷会被复制到**每一个**未来产品仓；
若 CI 是 loop 的 reusable workflow，**修一次，所有产品仓同时生效**。
这是"CI 必须做成 reusable workflow 而不是模板文件"的最强论据。

### 2.3 升级：复用现成的第 8 环，不新造机制

把 `Cloudbird-Software/loop` 自己登记进每个产品仓的 `UPSTREAM.yaml`
（`seam: control-plane`，`pin: <tag>@<sha>`，走 `min_age_days` 冷静期，写 `degrade_path`）。

loop 发新 tag → 各产品仓的 upgrade 环冷静期后自动开 "bump loop_version" 的 PR
→ 跑 bench 重放 → 四指标不劣化才允许合。

于是"每个产品仓都在用最新实践"变成一个**可观测、可回退的自动流程**，而不是靠人记得同步。

### 2.4 一致性：靠门禁强制（`gate/loop-conformance`）

在 loop 仓实现，由产品仓 reusable 调用，校验：

1. `LOOP.yml` 存在，且 `loop.version` 在支持窗口内（落后 ≤`max_lag_tags` 且 ≤`max_lag_days`，
   先 warn 后红）；`loop.sha` 是 40 位十六进制，不是 `latest` / `main` / 浮动 tag。
2. 必需文件齐全：`CHARTER.md` / `AGENTS.md` / `contracts/` / `tests/acceptance/` /
   `.github/CODEOWNERS` / `.loop/verify.sh`。
3. CODEOWNERS 覆盖全部敏感路径。
4. 薄壳 workflow 未被本地魔改（逐字比对 loop 侧同名文件）。
5. 产品仓内不存在 loop 机制目录的副本（CHARTER Q7）。
6. `LOOP.yml` 声明的 secrets / variables / environments 实际可用
   —— **只检测、只开 Incident、绝不自动修**（CHARTER N3）。

### 2.5 种子层的漂移

种子文件（`LOOP.yml`、薄壳 workflow、CODEOWNERS）后来在 loop 侧演进了怎么办：

- 让种子尽量小且稳定。
- 确需演进时，由 loop 的 `template-sync` workflow 按 `products.yml` 注册表 fan-out
  （`repository_dispatch` + App token）向各产品仓**开 PR**（`open_pr_only: true`）。
- 产品仓侧照常过全部门禁 + 强模型验收 + 复现，**不因为"来自 loop"而享受任何豁免**。
- `CHARTER.md` 与 `LOOP.yml` 是 `create-only`：人类的东西与产品自己的 pin，永不被覆盖。

### 2.6 注册表

loop 仓维护 `products.yml`，列出所有产品仓。
fan-out、合规巡检、scribe/canary/conductor 的跨仓目标，全部以此为唯一真源，
不再散落硬编码的 `product-x` 字面量。

## 3. 复制前必须先解决的两个既有问题

### 3.1 product-x 没有 `CHARTER.md`

`DECISIONS.md` 末尾"待办"已记录在案：所有卡的 `charter` 字段仍用 `["G0"]` 占位。
CHARTER 是唯一人类亲手写的东西，模板里必须留成可用内容，
否则复制出去的仓从第一天就带占位符债。

→ 已由 AI 代拟：`templates/product-x/CHARTER.md`（含机器可读索引，
`conductor/materialize.py` 的 `load_charter_ids()` 能直接解析）。
文末 `last-human-edit: PENDING` 标记它尚未经人类审读。

### 3.2 F-002 / C-015：`ci.yml` 缺 `merge_group` 触发器

现在复制模板 = 把这个卡死缺陷复制到每一个未来产品仓。
**必须先修 C-015，再动模板化**（WAVE-10 → WAVE-13 的硬依赖）。

---

## 4. 与"未来新研究"的接口

产品仓侧不需要为新研究做任何改动：新 lens 由 `LOOP.yml` 的 `lenses.enabled` 开关启用，
新评审器由 loop 侧路由决定，新策略参数在 loop 侧 `policy.yml`。
产品仓感知到的唯一变化是 `loop.version` 的 bump——而它已经有自动升级 + 重放 + 回退。
