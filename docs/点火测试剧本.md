# 《点火测试剧本》— loop v0.1.1 沙盒点火测试

> 本剧本对应任务书第 1 波（点火）。前置：第 0 波 F1 已合、`v0.1.1` 已封。
> 人照着本文一步步做即可。每一步都标了【谁做】：`【agent】`= 规划/ops 沙盒（本仓库的 AI），`【human】`= 你。

---

## 0. 核心约束（先读，整本都受它约束）

> **人进不去任何 impl 沙盒。** 人在 Trae 上对一个 impl 沙盒唯一能做的事是：**建沙盒时填好七槽位 + 把 `P0` 全文当作开场白粘进去**（"创建即开会话"——这一粘就替代了旧设计里点击器粘 P0 的活）。建完之后：**不能进沙盒 shell、不能给沙盒命名（UI 名是 Trae 自动给的，但 `LOOP_SANDBOX_ID` 这个环境变量槽位你能填，所以"起名 impl-file"实际就是填 `LOOP_SANDBOX_ID=impl-file`）、不能和沙盒里的 AI 实时对话、不能打开沙盒看内部。**
>
> 因此所有观察只能走两条外部通道：
> 1. **Trae 会话面板**——你能看到 impl 沙盒的对话流，**确认弹窗（"是否运行此命令？"）只会出现在这里**。T-f 就是数这里出现的弹窗数，目标是 0。
> 2. **GitHub**——`product-x` 仓库的 commit / branch / PR / issue 评论。agent 跑 `loop save` 会出现 commit，`loop done` 会出现 PR/评论。你用浏览器看 GitHub 即可。
>
> **进度同步协议**：本仓库的 ops AI（你正在对话的这个）会用提问的方式告诉你"现在去做 X"。你做完 X 就回答一句（哪怕只回"done"），ops 就知道动作完成了，再推进下一步。**任何需要"进沙盒杀进程/敲命令"的环节都被砍掉**：杀进程（T-b）由本地 smoke + E2 僵尸测试替代覆盖，你只需让会话里的 agent 跑一句 `loop status` 证明守护进程活着。

## 3. 点火探针卡（IPC）【agent 造，人只在需要时配合】

### 为什么需要探针卡
P0 第 1 步是 `loop next`（取卡），第 3 步才是 `loop save`。**没有 ready 卡时 `loop next` 会一直阻塞**，agent 永远跑不到 `loop save`，T-a（save→commit）就出不来。第 1 波还没开 WAVE-1 的 5 张真卡（那是第 2 波 E1 的事），所以 **ops 必须先在 product-x 上造点火探针卡**：一张给 impl-1（IPC-1），一张给 impl-file（IPC-2），paths 互不交叉避免抢卡冲突。

> **造卡方式二选一**（§0 末尾的提问里 ops 会问你选哪个）：
> - **A【推荐】**：人把一枚有 `product-x` 的 Issues/Contents 读权限的 PAT 给 ops，ops 在对的时机（先造 IPC-1，等 impl-1 领走再造 IPC-2）用 `gh issue create` 造卡。这样时机由 ops 控，impl-1 不会抢走 IPC-2。
> - **B**：人按 ops 的信号，在 GitHub 网页上 product-x → New issue，把下面给的标题+正文粘进去提交（两次，分时机）。PAT 不出本对话。

### 造卡时机（ops 控制，A 方式下人不用管；B 方式下按 ops 信号造）
1. impl-1 建好且确认卡在 `loop next` 等卡（T-d 已观测）→ ops 造 **IPC-1**。
2. impl-1 领走 IPC-1、跑完 `loop done`（PR 出现在 product-x）→ ops 造 **IPC-2** 给 impl-file。

> 这样避免 impl-1 在等卡期把 IPC-2 也抢了（impl-1 跑 IPC-1 时是 `claimed`，paths `ignition/impl-1/**` 与 IPC-2 的 `ignition/impl-2/**` 不交叉，done 之后若 IPC-2 已在队列会被 impl-1 顺手领走——所以 IPC-2 必须等 impl-1 停手再造）。

## 4. 六测【human 观测 + ops 配合】

> 观测规则：弹窗只数 Trae 会话面板里出现的"是否运行此命令"类确认框；commit/PR 只看 GitHub `product-x`。每项给【操作 / 预期可观察 / 失败分支】。

### T-a 零弹窗 save【不动，原生流程】
- **操作**：impl-1 建好粘 P0 → ops 造 IPC-1 → agent 自主 `loop next` 领卡 → P0 第 3 步 `loop save "wip"`。
- **预期可观察**：product-x 出现 `agent/ignition-probe-1` 分支 + 一条 draft PR；**Trae 面板全程 0 弹窗**。save 消息可能是 `wip`（P0 原文）或 `ignition probe`（探针任务后 save），都算通过。
- **失败分支**：见 §5 表 F-3 / F-5。

### T-b 守护进程健康【砍掉杀进程，改跑 loop status】
- **操作**：你进不去杀进程，所以**不杀**。替代覆盖：本地 smoke 已验"loopd 被 kill 后重启不丢工作"（见 `.loop/smoke.sh` g 项），系统层恢复由第 2 波 E2 僵尸测试（销毁会话＝你能做的"杀沙盒"）验。本测只让会话里的 agent 跑一句 `loop status`——这句已包在 IPC-1 任务第 1 步里，agent 会自主跑。
- **预期可观察**：`ignition/impl-1/status.txt`（出现在 IPC-1 的 commit/PR 里）含 `=== loopd status ===` 与 `daemon: alive (pid=…)`；**0 弹窗**。若 agent 在会话面板里直接贴了 `loop status` 输出也行。
- **失败分支**：见 §5 表 F-2。

### T-c file 模式【另开 impl-file 沙盒】
- **操作**：**另开一个沙盒**，槽位与 impl-1 完全一致，**唯一区别**：`LOOP_IO_MODE=file`、`LOOP_SANDBOX_ID=impl-2`（即"起名 impl-file"=填这个 `LOOP_SANDBOX_ID`）、`LOOP_MODEL` 选**另一家**模型（保证池内多样）。开场白同样粘 P0 全文。建好后 ops 造 IPC-2（§3 时机 2）。
- **预期可观察**：impl-file 自主 `loop next`（file 模式下 loopd 的 `filemode_thread` 已开）→ 领 IPC-2 → `loop save` → `loop done`；product-x 出现 `agent/ignition-probe-2` 分支 + draft PR；**全程 0 弹窗**（file 模式本就是弹窗的退路，这里验它"开着也不坏事"）。
- **失败分支**：见 §5 表 F-4 / F-6。

### T-d 空队列阻塞【不动，纯观察】
- **操作**：impl-1 建好粘 P0 后、IPC-1 还没造的窗口期；以及 impl-1 跑完 IPC-1 后回到 `loop next` 的窗口期。不用你做任何事，只看会话面板。
- **预期可观察**：agent 报告在等卡（`loop next` 在轮询 outbox），**不报错、不退出、0 弹窗**。观察 1–2 分钟即可（`LOOP_NEXT_BLOCK_SEC=1500`，满 25 分钟才返回 EMPTY 再重试，不用等满）。
- **失败分支**：见 §5 表 F-7。

### T-e 白名单意图【不动】
- **操作**：让会话里的 agent 跑 `loop run logs.tail`——已包在 IPC-1 任务第 2 步里，agent 自主跑。
- **预期可观察**：`ignition/impl-1/tail.txt`（在 IPC-1 的 commit/PR 里）是 `tail -n 200 .loop/logs/app.log` 的输出，**不含 `UNKNOWN_INTENT`**；**0 弹窗**。这同时验了 F1 修的 intents 三段查找（`/usr/local/etc/loopd/intents.yaml`）。
- **失败分支**：见 §5 表 F-8。

### T-f 弹窗计数【贯穿全程】
- **操作**：从 impl-1 开会话粘 P0 起，到 impl-file 跑完 `loop done` 止，**人数 Trae 会话面板里出现的确认弹窗总数**。
- **预期可观察**：**0**。任一非零即核心命题"消灭命令确认"未被证实，按 §5 表对应分支修。
- **失败分支**：见 §5 表 F-1（任一弹窗）。

## 5. 失败分支表【人按此贴日志给 ops 修】

| 编号 | 失败现象 | 最可能原因 | 要贴回给 ops 的证据 |
|---|---|---|---|
| F-1 | T-f 数到弹窗（任何 `loop`/编辑被要求确认） | Trae 把 `loop` 当可疑命令；或沙盒权限模式没设成"自动批准编辑/命令" | 会话面板弹窗截图 + 触发弹窗的那条命令原文 + `/work/.loop/logs/loopd.log` 末 50 行 |
| F-2 | `loop status` 报 `LOOPD_BOOT_FAILED` / `daemon: MISSING` | loopd 没起或崩了；supervisor 没拉起 | `loop status` 全文 + `/work/.loop/logs/loopd.log` 全文 |
| F-3 | `loop save` 后 product-x 无分支/PR | push 被拒：PAT 缺 Contents 写权限，或 ruleset 拦了分支推送 | loopd.log 里 `git push` 段的 stderr + PAT scope 列表 |
| F-4 | impl-file 跑不通 next→save→done | file 模式下 agent 不会写 IN.json（P0 只在弹窗时才切 file） | impl-file 会话面板对话流 + loopd.log |
| F-5 | bootstrap 校验失败 `SHA_MISMATCH` | 拉到的 bootstrap.sh 与 v0.1.1 不符（tag 被动 / 网络中间人） | bootstrap 输出的实际 sha256 + `git ls-remote --tags origin v0.1.1` |
| F-6 | impl-file 不领卡 | IPC-2 还没造 / 造错 paths / impl-1 抢先领了 | `gh issue list -R product-x --label card --state open` 输出 |
| F-7 | `loop next` 报错或退出 | loopd 崩 / token 失效导致 `gh issue list` 抛错 | loopd.log 末 100 行 + `loop status` |
| F-8 | `loop run logs.tail` 返回 `UNKNOWN_INTENT` | intents.yaml 没落地 `/usr/local/etc/loopd/intents.yaml`（bootstrap 第 2 步失败） | `ls -l /usr/local/etc/loopd/intents.yaml` + `loop run logs.tail` 全文 |

## 6. 修-测循环规则

1. 任一测红 → 人按 §5 把对应日志贴回给 ops。
2. ops 判定根因：
   - 若根因在 **loop 仓库代码/bootstrap**（如 intents 路径、loopd bug）→ 走 F1 流程：修 → smoke 全绿 → 提 main → `git tag v0.1.2`（或递增）→ `git push origin v0.1.2` → 重算 `LOOP_BOOTSTRAP_SHA256`（对新 tag 的 `loopd/bootstrap.sh`）→ 若 `prompts/` 动了也重算 `LOOP_PROMPTS_SHA` → 更新 `Trae沙盒填写卡.md`（`LOOP_BOOTSTRAP_REF=v0.1.2` + 新哈希）→ **重建沙盒重测**。
   - 若根因在 **沙盒配置 / Trae 权限模式 / PAT**（非仓库问题）→ 改沙盒槽位或权限模式，不重封 tag，直接重建沙盒重测。
3. 重测从 §2 重新建沙盒开始（旧沙盒作废，可留着对比）。
4. 六测全绿 = 核心命题"消灭命令确认"被证实，进第 2 波。
