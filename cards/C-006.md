## 背景

[tick.py](../conductor/tick.py) 的 11 件事代码全在，但 [conductor.yml](../.github/workflows/conductor.yml) 要靠 `secrets.CONDUCTOR_APP_ID/KEY` + org App 安装（OPC v4 Day 0 步骤 5/6，纯人工未做）。结果：升档、依赖放行、plan inbox 打包、48h 放行全 dormant。"内部开发管理"的自愈少了一大半。loopd 自带 reaper 只兜底僵尸回收，其余 10 件事没跑。

## 要做什么（二选一，推荐方案 B）

**方案 A（重，原架构）**：建 conductor App，走 OPC v4 Day 0 步骤 5/6。
- 装 GitHub App、配 secrets.CONDUCTOR_APP_ID/KEY、org 安装。
- 工作量大，但与正式体系无缝衔接。

**方案 B（轻，推荐，因沙盒已能直接跑命令）**：把 tick.py 关键几件搬进轻 cron / 搬进 loopd。
- 在 [loopd.py](../loopd/loopd.py) 加一个 verb（如 `loop tick`），调 tick.py 的关键函数。
- 由 P-continue agent 在每次"继续"时调一次 `loop tick`，或外部 cron 触发。
- 至少跑通：僵尸回收、依赖放行、plan inbox 打包、48h 静默放行。
- 优势：不依赖 conductor App，沙盒直接跑。
- 劣势：自愈靠"继续"触发或外部 cron，不是 GitHub 原生事件驱动。

选 B 时，在 [tick.py](../conductor/tick.py) 顶部注释标明"暂行期由 loop tick 调用，conductor App 建好后切回原生 workflow"。

## 不要做什么

- 不要把 11 件事全搬（race/occurrences/audit 分片等可后补，先搬僵尸/依赖/plan inbox/48h 放行这 4 件关键的）。
- 不要破坏 [tick.py](../conductor/tick.py) 现有签名（materializer/conductor workflow 仍要能调）。
