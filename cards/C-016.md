## 背景

[F-003](./F-003.md) 复现确认：conductor/tick.py 第 212 行写 `if st != "closed":`（小写），但 `gh issue view --json state` 实际返回大写 `"CLOSED"`，导致 unblock_deps 永远不触发 — 任何 blocked 卡的上游 issue 被 close 后，下游卡永远卡在 `state: blocked`，dep pass 路径完全失效。本沙盒复现：

- 命令：`gh issue view 67 -R Cloudbird-Software/product-x --json state`
  实际输出：`{"state":"CLOSED"}`
- 命令：`gh issue view 67 -R Cloudbird-Software/product-x --json state --jq '.state'`
  实际输出：`CLOSED`
- 构造 #67 closed + #69 blocked, blocked_by=[67] → 跑 `python3 conductor/tick.py` → `[3] Unblock dependencies...` 行后无 unblock 输出；复检 #69 body：`state: "blocked", blocked_by: [67]` 未变。
- tick.py:212 源码：`for dep in blocked_by: ... if st != "closed": all_merged = False; break`（客观可读 [conductor/tick.py:212](file:///workspace/loop/conductor/tick.py#L212)）。

旁证：tick.py 全文仅 line 212 一处与 gh 输出的 state enum 直接比较；line 97/148/227/558 的 state 比较对象是 loop block 内部状态（`claimed` / `in_progress` / `ready` / `blocked`），由 inject_block 自己写，不受 gh 大小写影响。

## 要做什么

1. 最小修复：tick.py:212 改为 `if st.lower() != "closed":`（或等价的 `st = json.loads(p.stdout or "{}").get("state","").lower()` 然后 `if st != "closed":`）。
2. 重跑 V-006 Scenario B（同 #67 closed + #69 blocked_by=[67] 构型）：tick 输出应含 `→ #69 unblocked (all deps merged)`，#69 body `state: "blocked", blocked_by: [67]` → `state: "ready"`。
3. 如有 contract 测试覆盖此处逻辑，保留测试一致；不要扩面（只修 line 212 一处）。
4. 验收后给 V-006 翻 ready（如本卡 status: done 时 V-006 仍是 pending：翻 V-006 ready 为 true，重跑 verify → VERDICT=PASS）。
