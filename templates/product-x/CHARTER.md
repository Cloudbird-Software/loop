## P 产品是什么（一句话）

product-x 是 LOOP 体系的**参考实现样板仓库**：它自身端到端跑通"接单→实现→异构验证→强模型验收→复现→合并"的全闭环，
并以最小、可复制的形态，向未来的产品仓库示范"一个正确接入 loop 控制面的产品仓应该长什么样"。

## U 用户与场景

- **U1 未来产品仓库的创建者（人类）**：用 product-x 作为 GitHub template 生成新产品仓，
  期望改动 ≤5 处（产品名、CHARTER 的 G/Q/U 段、`LOOP.yml` 的 lens 集合、CI 的语言栈、CODEOWNERS）即可开工。
- **U2 进仓干活的 AI 工作单元**：冷启动、无人类在场，只凭仓库内容就能判断"我该干什么、干到什么程度算完、谁来验我"。
- **U3 loop 控制面自身**：把 product-x 当作唯一的端到端集成测试床——loop 的任何机制变更，
  必须先在 product-x 上被证明可工作，才允许 fan-out 到真实产品仓。

## G 本季度目标（可判定）

### G1 端到端可用，而不只是"可工作"

> "可工作" = 每个部件单独跑得动。"可用" = 一个不了解本体系的人/AI，
> 按仓库内的说明从零开始，能不问任何人地走完一整轮并得到确定性结果。

判定：见 Q1、Q2。

### G2 门禁真实拦截，零假绿

> 名义上的 required check 必须真的能红。任何"探不到文件就 SKIP 且 exit 0"、
> "`|| true`"、"`set +e` 吞掉退出码"的模式，在本仓库一律视为缺陷而非权宜。

判定：见 Q3。

### G3 验证与验收独立可信

> 实现方不得自证。验证工与实现工必须异构（不同模型），且异构由机器强制而非文档约定；
> 强模型验收只产出可证伪断言，断言必须被独立复现才能进入修复。

判定：见 Q4、Q5。

### G4 作为样板可被复制，且复制品持续对齐最新实践

> 复制出去的产品仓不允许持有 loop 机制的副本，只允许持有对 loop 的 pin 引用。
> loop 发布新实践后，各产品仓自动收到升级 PR，并由确定性门禁校验其对齐度。

判定：见 Q6、Q7。

## N 绝不做（红线；AI 提了自动驳回。**复制到真实产品仓时必须原样继承**）

- **N1 不让任何开源件接管跨卡调度。** 单卡执行器可以外包（opencode / Codex CLI / Copilot CLI），
  跨卡的派单、租约、回收、依赖放行永远由 loop 自己的 conductor 持有。
- **N2 不做无外部可观测收益的重构。** "更优雅""更现代""更符合最佳实践"都不构成理由；
  必须能指出一个外部可观测的指标变化。
- **N3 不自动修正 GitHub branch ruleset / 组织权限 / secrets。**
  检测到漂移一律开 Incident 并停在那里等人类，永不自动写回。
- **N4 不从非官方源安装任何依赖。** 每个外部依赖必须登记进 `UPSTREAM.yaml`，
  钉到完整 SHA，过冷静期，且带 `degrade_path`。
- **N5 不把假绿当作权宜之计。** 宁可让流水线红着、让波次停住，也不允许用
  `|| true` / `set +e` / 探不到就 SKIP 的方式把失败伪装成成功。
  临时不可用的能力必须显式失败并说明原因。
- **N6 不允许实现方自证。** impl 不得给自己的卡产 VERDICT；
  评审模型不得给自己的 claim 做复现判定；任何"同一模型既做又验"的路径一律作废。
- **N7 不把模型的论断当作事实。** 强模型（含最强模型）的输出只是"待检验的输入"，
  不可证伪的论断一律拒收，未被独立复现的论断不得触发任何代码改动。
- **N8 不在 product-x 样板里塞真实产品逻辑。** 样板只示范 LOOP 体系；
  一旦开始承载真实业务，它就不再是样板。
- **N9 不在产品仓复制 loop 的机制文件。** 只允许 pin + reusable workflow 引用。
- **N10 不把高权限凭证放进仓库级 secret。** 每个 token 按最小权限拆分，
  能用 `GITHUB_TOKEN` 的绝不用 PAT，能用 GitHub App 的绝不用 PAT。
